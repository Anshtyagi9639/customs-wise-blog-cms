# Storing blog images on Cloudinary

When Cloudinary is configured, images uploaded in the CMS are stored on Cloudinary, and the CMS keeps only a record of each one (in MongoDB when that is configured, otherwise in the JSON file). With nothing configured, new images go to the local folder `data/uploads` as before.

**Connecting Cloudinary does not make the CMS ready for the internet.** There is still no sign-in and no per-website permissions. Keep the dashboard on this computer until authentication is built.

## Set it up

1. Sign in to Cloudinary and open **Settings > API Keys**. The free plan is enough; nothing here needs a paid plan.
2. Note three values: the **cloud name**, an **API key** (a number), and that key's **API secret**. Consider creating a key just for the CMS, so it can be disabled on its own later.
3. In the CMS project folder, copy `.env.example` to `.env.local` if you do not have one yet. Open `.env.local` in an editor and set:

   ```
   CLOUDINARY_CLOUD_NAME=...
   CLOUDINARY_API_KEY=...
   CLOUDINARY_API_SECRET=...
   ```

   Type or paste the values there yourself. Do not put them in a chat, ticket, screenshot or any file that is committed. `.env.local` is ignored by git.
4. Check the account details:

   ```
   npm run check:cloudinary
   ```

   It says which settings are present and whether Cloudinary accepts them. It never prints the key or secret. To also prove an upload works, run `npm run check:cloudinary -- --upload-test`: it uploads one small test image to a `cms-connection-test` folder and deletes it again.
5. Restart the CMS if it was started with `npm run start:local` (`npm run dev` picks the change up by itself). `http://127.0.0.1:3100/api/health` shows `"images":"cloudinary"` when image hosting is in use.

All three settings are needed. If only some are set, uploads are refused with a message naming the missing one; the CMS does not quietly fall back to the local folder.

`CLOUDINARY_URL`, the SDK's own single-variable setting, is not needed. If your account must upload to a regional address (for example an EU data centre), that is the place to set it; the three variables above still decide which account is used.

## What happens on upload

1. The editor chooses an image. The editor shows "Uploading…".
2. The browser sends the file to the CMS server (`POST /api/admin/sites/{website}/media`). The browser never talks to Cloudinary directly and never sees the API secret.
3. The server checks the file: real type read from its first bytes (JPEG, PNG, WebP, AVIF or GIF; the file name and the browser's stated type are not trusted), size up to 5 MB, readable dimensions. Anything else is refused and nothing is sent to Cloudinary.
4. The server uploads to Cloudinary with a signed request.
5. Only after Cloudinary confirms does the server save the record. The editor then shows the preview, where the image is stored, and the alt text field.
6. Saving or publishing the article stores the image's `https://` address and alt text in the article.

### Where images go

| Website | Cloudinary folder and public ID |
| --- | --- |
| Customs Wise (test configuration) | `customs-wise/blog/<generated name>` |
| Demo Website | `demo-website/blog/<generated name>` |

The name is generated by the CMS (a timestamp plus random characters). Nothing from the uploaded file's name is used. Uploads are sent with overwrite turned off, so an existing image can never be replaced; if a name ever clashed, the upload is refused and the editor is asked to try again.

Every upload is tagged `blog-cms` and `blog-cms-site-<website>`, and carries the record's id in its context (`cms_media_id`).

On accounts in Cloudinary's older "fixed folders" mode the folder comes from the public ID alone; on "dynamic folders" accounts the same folder is also set as the asset folder so it appears in the Media Library. Verified on a real dynamic-folders account; a fixed-folders account has not been tried.

### What the record holds

`id`, `siteId`, `storage` (`cloudinary` or `local`), `publicId`, `url` (the `https://res.cloudinary.com/...` address), `fileName`, `originalName`, `mime`, `bytes`, `width`, `height`, `alt`, `createdAt`. No image data is stored in the database.

Alt text is entered per article. The record's `alt` is updated to the alt text most recently saved with that image.

An article may only use an image that its own website has a record for, with exactly the recorded address. An address typed in by hand, another website's image, or an image on any other host is refused.

## Existing images

Images uploaded before Cloudinary was configured stay in `data/uploads` and keep working: each record says where its file is, and the CMS still serves local files at `/media/...`. Nothing is moved, deleted or bulk-migrated. Do not delete `data/uploads`.

## When something goes wrong

| What the editor sees | Cause | What to do |
| --- | --- | --- |
| "Image hosting is not fully set up: … missing from .env.local" | One or two of the three settings are empty | Add them, restart the CMS |
| "Cloudinary did not accept the configured account details" | Wrong cloud name, key or secret, or the key was disabled | Run `npm run check:cloudinary`; copy the values again; restart |
| "Cloudinary did not recognise the configured cloud name" | Cloud name mistyped | Correct `CLOUDINARY_CLOUD_NAME`; restart |
| "Cloudinary could not be reached" | No internet connection, or a firewall or proxy blocking `api.cloudinary.com` | Check the connection |
| "Cloudinary is limiting uploads for this account" | Plan limits reached | Wait, or check usage in the Cloudinary console |
| "That file is not a supported image" / "The limit is 5 MB" | Refused by the CMS before upload | Use a supported image under 5 MB |

The server log records only the HTTP status and the kind of error. Cloudinary's own error text is never logged or shown, because it can contain the cloud name or API key.

A change to `.env.local` takes effect only after the CMS is restarted.

### Orphaned assets

An orphan is an image on Cloudinary that no record points to. The CMS avoids creating them:

- A record is written only after Cloudinary confirms the upload, so a failed upload leaves no record.
- If the upload succeeds but the record cannot be saved (for example the database is down), the CMS deletes the upload again. If that deletion also fails, the server log has a line starting `[images] … ORPHANED ASSET left on Cloudinary:` followed by the public ID.

To list any that exist:

```
npm run check:cloudinary -- --orphans
```

This compares everything on Cloudinary tagged `blog-cms` with the records and prints the public IDs that have no record. It deletes nothing. Images that were uploaded but never used in a saved article are *not* orphans by this definition: they have records. Removing an article or replacing its image does not delete the image from Cloudinary; there is no clean-up of unused images yet.

## Tests

```
npm run test:cloudinary-mock
```

runs 49 checks against a stand-in for Cloudinary on this computer (see the top of `scripts/test-cloudinary-mock.mjs` for how to start the CMS for it). It covers: successful upload, HTTPS address, per-website folder, generated public ID, no overwrite, signed request without the secret, refusal of invalid and oversized files before upload, five kinds of Cloudinary failure plus Cloudinary being unreachable, no record on failure, removal of an unusable upload, an upload whose record cannot be saved (the upload is taken down again and no record is left), articles and pages using hosted images, refusal of other websites' and forged image addresses, and existing local images.

It proves how the CMS behaves. It does not prove that a real account works; use `npm run check:cloudinary -- --upload-test` and `npm run test:live` for that (see docs/MONGODB_ATLAS.md).

Setting `CMS_IMAGES=local` keeps new images in the local folder even when Cloudinary is configured. It exists for test runs.

## Not done in this step

- No sign-in or permissions (unchanged; required before any public deployment).
- No resizing, cropping or format conversion: the stored address is the original image. Cloudinary can deliver smaller versions through its URL options later.
- No deletion from Cloudinary when an article or image is removed, and no media library screen.
- Existing local images were not moved to Cloudinary.
- The case "upload succeeded but the record could not be saved" is tested with the mock only, not against the real account (it cannot be provoked safely there).
